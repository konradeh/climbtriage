# 03 — Stack decisions and tradeoffs

Each decision below names what would make us revisit it.

| # | Decision | Why | Cost / risk | Revisit when |
|---|---|---|---|---|
| S1 | **Kotlin + Jetpack Compose + coroutines/Flow**, single `:app` module with package-level layering | Default Android stack. One module keeps the build simple while boundaries are enforced by package and interface. | Package boundaries are enforced by review, not by the compiler. | A second consumer appears (for example a KMP shared core for iOS). Then split `:core-contracts`, `:core-geometry` and `:perception` into modules. |
| S2 | **CameraX `VideoCapture` + `Recorder`** to app-private storage, back camera, no live inference in M1 | Recording is independent of inference by construction. | No live overlay yet. | M4 (live feedback). Add an `ImageAnalysis` use case with `STRATEGY_KEEP_ONLY_LATEST`, which bounds the queue by dropping frames. |
| S3 | **Media3 ExoPlayer** for replay, overlay drawn in a Compose `Canvas` | Accurate position, handles rotation metadata, and M2 export can use Media3 Transformer. | Overlay timing follows `currentPosition`, which updates at frame rate; the overlay can lag by up to one frame. | Frame-accurate export (M2): use a Transformer `OverlayEffect`. |
| S4 | **Frame access**: `MediaExtractor` for PTS and `MediaMetadataRetriever.getFrameAtIndex` for decode | Real timestamps from the container. Simple and adequate for offline analysis at 5–15 fps. | `getFrameAtIndex` is slower than a `MediaCodec` + `ImageReader` pipeline. | The analysis time on reference phones is unacceptable, or live analysis is needed. |
| S5 | **MediaPipe Pose Landmarker (full), IMAGE mode, `numPoses=3`**, model bundled in assets | Apache-2.0, on-device, 33 landmarks including **heel and foot index**, which the reference's COCO-17 lacks. IMAGE mode is stateless, so detections are replayable. | The model card targets single-person video. Climbing has occlusion and inverted poses. **This is unvalidated on climbing** (see `07`). No identities, so we built our own tracker. | Evaluation shows unacceptable recall on climbing poses. Candidates: ViTPose+ offline via backend (Apache-2.0 weights, but check training-data terms), RTMPose via ONNX Runtime Mobile. |
| S6 | **Room** for metadata; large dense data (pose detections) as versioned JSON files in app-private storage and referenced from Room | Room keeps queries and migrations. JSON files are portable and match the backend contracts. | Two stores to keep consistent. Deletes go through one repository. | Pose data grows past what JSON handles well. Switch to a binary columnar format behind the same repository. |
| S7 | **kotlinx.serialization** for contracts | Compile-time, no reflection, and multiplatform-ready for iOS/KMP. | — | — |
| S8 | **Backend: Python 3.11+ (tested on 3.14), FastAPI, NumPy, OpenCV (headless), Pydantic v2** | Same ecosystem as the reference and as CV research. | Two languages. Contracts are kept in sync through JSON Schema plus golden-file tests on both sides. | — |
| S9 | **Hold segmentation baseline: SAM 3.1 through the VLM Run gateway**, behind a `HoldSegmenter` adapter | This is the reference approach, and we verified that the gateway documents `segment`, `track` and `segment_box`. It needs no training data. | Third-party dependency. Pricing is not documented on the model page, and the terms need review. Latency is unmeasured. The Meta SAM licence restricts some uses. **It has not been run in this environment, because no API key was available.** | We benchmark self-hosting SAM 3.1 (GPU cost) or a compact fine-tuned segmenter (M4). |
| S10 | **Generic prompt "climbing hold" (plus "climbing volume")**, with route membership computed on our side | Keeps wall holds separate from the route, which a colour prompt cannot do (the reference prompts per colour). | More candidates to review. Colour estimates depend on lighting. | — |
| S11 | **Offline hold assist: on-device colour-cluster heuristic**, labelled `heuristic.colourassist.v1` | Gives offline users *some* help without pretending to be a detector. | Weak on chalky, multi-colour or low-contrast holds, and not evaluated against targets. | An on-device model passes `07` gates. Candidates: ONNX Runtime Mobile with a distilled segmenter. |
| S12 | **Jobs: SQLite (dev) or PostgreSQL (prod) + a queue interface**. Dev uses the table as a durable queue; prod uses Azure Service Bus. Blobs go to the local FS in dev and Azure Blob Storage in prod. Deployment is Azure Container Apps. | Portable, and no cloud is needed locally. | The dev SQLite queue is single-node. | Multi-worker scale-out needs Service Bus or Postgres `SKIP LOCKED`. |
| S13 | **No Kubernetes** | Container Apps covers the API, workers and scale-to-zero. | — | Demonstrated need (GPU node pools for self-hosted models). |
| S14 | **Android toolchain**: AGP 9.4.1 (built-in Kotlin), Kotlin 2.3.21, KSP 2.3.12, Gradle 9.8.0, compileSdk 37, targetSdk 36, minSdk 28, JDK 21 | minSdk 28 provides `getFrameAtIndex`. compileSdk 37 is required by current AndroidX (core 1.19, Compose UI 1.12). targetSdk stays at 36 until behaviour changes are reviewed. | Devices older than Android 9 are excluded. On the build machine, Windows Application Control blocked AGP's Maven aapt2, so `tools/setup-toolchain.sh` points AGP at the SDK's aapt2. | Market data demands it; targetSdk 37 review. |

## Things that must stay swappable

The following sit behind interfaces: `PoseEngine`, `HoldCandidateSource`,
`HoldSegmenter` (backend), `PoseProvider` (backend), `JobStore`, `BlobStore`,
`FrameSource`, `DepthSource`, and `ContactInferencer`.
